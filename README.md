# MobileWork Windows 本地验证控制台

代码仓库：[yufeinever/mw-auto](https://github.com/yufeinever/mw-auto)。仓库包含源码、44项脚本、功能目录、测试和版本文档；原设备运行记录与截图保留在本机，克隆后可以生成新的测试记录。

独立版本 v0.0.23。监听 **http://127.0.0.1:17866**，通过 MobileWork 主窗口 CDP **127.0.0.1:9223** 执行。

v0.0.23补充协议覆盖：页面HTTP响应协议/连接对端、WebSocket握手及收发帧、SSE事件与数据块、NetLog的UDP/QUIC传输事件、进程树UDP本地绑定。覆盖表明确区分本批未观察到、未启用、不可用、采集不完整及旧批次未采集。详见[协议覆盖梳理](docs/接口探测协议覆盖梳理-20261027.md)。

接口探测页：**http://127.0.0.1:17866/probe**。可独立选择应用接口（页面 CDP）、网络链路（Chromium NetLog）、进程归属（MobileWork 进程树 TCP / UDP 采样）。选静置基线或功能遍历，点击开始，等待对应层显示记录中，再操作 MobileWork；手动停止或1/5/15分钟自动停止后生成汇总。网络层停止后才解析；页面层可实时计数。所有采集在后台进行，不自动触发产品业务操作。

结果包括方法/归一化路径/地址类型、HTTP状态、传输失败、未完成、RPM/平均RPS/峰值秒请求、响应头及完整下载的P50/P95/最大值、同资源间隔，以及PID/远端地址/连接状态。WebSocket帧、SSE事件及数据块、UDP本地绑定分别列出。可标记静置与功能操作开始时间，历史记录和导出JSON位于 `data/probes/`。默认最多15分钟、每段32MB追踪缓冲、整批25万条允许的NetLog事件及64MB脱敏文件；每60秒回收再启一段，间隙和超限显式标为部分采集，不能作为连续无缺口的全量计数。

这是部分客户端网络覆盖：未接入Electron主进程 `session.webRequest`；NetLog仅覆盖Chromium网络栈，不能覆盖所有Node.js原生HTTP或子进程接口。三层不可简单相加，连接采样不是请求次数，2xx不是业务成功。单客户端频率反映观测调用量，不能测出后端CPU、容量或实际处理耗时。完整路径仍需客户端侧埋点支持，不要求提供生产服务端日志。

原生接口参考：[Electron webRequest](https://www.electronjs.org/docs/latest/api/web-request)、[Electron NetLog](https://www.electronjs.org/docs/latest/api/net-log)、[CDP Tracing](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/)。不替换现有webRequest监听器（该API每事件仅保留最后注册监听器），不修改安装包或开启系统全量抓包。NetLog事件在内存脱敏后才写入；请求头、正文、查询参数不落盘。路径模板复用允许词表，未知段折叠为`:id`，需按后续研发文档校准。

## 网络与模型响应诊断（v0.0.20）

每条用例自动订阅页面CDP网络事件，并从本轮起点增量读取模型代理日志。点击用例详情的“网络与模型响应”查看HTTP状态、响应头/请求结束耗时、失败以及同期模型路由和上游错误。JSON导出和Markdown报告保留同样的信息；独立热测分开保存预热和正式执行。

页面耗时仍按原输入事件到目标状态计量。网络观测是整个主窗口的同期流量，可能包括后台请求；模型代理日志全部标为“同期未归属”，不能凭时间接近就认定属于本用例。stream_end不代表回答成功，首字时间尚未采集，历史记录不倒填。采集故障仅记录，不阻塞队列或更改功能结果。

默认日志为当前用户的`.mobilework/electron/logs/main.log`；其他安装布局可通过环境变量`MW_MODEL_LOG_PATH`设置本地日志文件绝对路径，启动控制台时生效。日志缺失时CDP仍独立工作。每条最多保存160个请求和80个日志事件，溢出、轮转与读取缺口显示在详情；2秒保存一次快照，硬超时仅保证保留最后已上报的信息。

只保存允许的元数据；URL查询、认证头、动态路径原文、请求/响应正文均不记录。日志中的调用/Session/消息ID仅保存散列关联键。采集覆盖CDP连接成功之后的流量，应用启动前段和未观察到的首token不能补造。

前端修改`src/app.js`后执行`npm run build:console`，生成`public/app.js`；浏览器共享的展示模块仍在`public/`。本版没有实现自动造数、全平台启动或精确Session归属，后续方案见[执行设计](docs/延迟测试执行设计.md)。

## 当前执行策略（v0.0.19，用户明确调整）

单条失败、阻塞、超时或清理异常只记录；等待本脚本退出后执行下一条，不设置恢复锁、不等待人工解除。清理仍尽力执行，失败证据保留，后续脚本从实际页面重新检查自己的前置条件。手动暂停/停止按请求生效；仍不允许两个脚本同时操作MW。冷批次丢失应用进程或启动证据时仍不能冒充有效冷启动。

已停止旧批次的 schedulingHold 在新批次前解除，保留 holdRelease 审计、原 functional/restored/cleanupIssues/handoff，不改成恢复成功。旧脚本仍在运行时仅等待进程退出。旧 waiting_recovery 在服务升级后转为暂停，用户点击继续；已停止的旧批次不自动续跑。

016/023/037共用技能收尾：已打开弹层直接复用，等待控件就绪，精确匹配唯一技能名，恢复后读回验证；不依赖变化后的首行、不盲目再次点击技能入口。该修正已通过浏览器夹具验证，未在本轮启动真实MW复测。

## 一键执行与当前批次（v0.0.18）

- “一键执行所选”执行勾选项；未勾选时显示“一键执行全部”。弹框询问是否已在重启MW：已从托盘退出并重新打开时直接执行，控制台等待首页就绪；尚未重启时展开托盘指引，退出后可由控制台启动并执行。
- 同一批次先按所选顺序完整执行第1轮冷启动，再按同样顺序执行第2轮热启动，每项共2次，不增加预热、不取均值。冷、热各自保留结论、计时、开始/结束时间及恢复证据。单项异常仅记录，按v0.0.19策略继续下一条。
- 手动重启是用户确认，记录 `restartConfirmation.source=user_confirmed`；执行器只确认首页就绪，不假称检测到进程重启，不补造应用启动耗时。由控制台启动时仍要求旧进程全部退出并采集真实启动耗时。两种方式都只重启一次，第一轮后续操作共享进程，不能当作每个模块独立冷加载。
- 当前批次入队的轮次显示“等待执行”，开始后显示“运行中”，完成后显示本轮结果；停止后未执行的轮次标“未执行（已取消）”。不会将旧通过状态、旧耗时或旧时间填入当前排队项。历史批次仍可单独查看。
- 表格按冷/热两行显示启动和结束时间，北京时间精确到秒；未开始不填写启动时间，未结束不填写结束时间。进度按执行次数计算（44项两轮共88次）。
- 原“仅热启动”仍按旧规则先预热后记录第2次；“仅冷启动”及独立冷启动首页入口保留。命令行两轮：`node run.mjs --all --restart-confirmed`，或托盘退出后 `node run.mjs --all --launch-after-exit`。默认无这些参数时保持仅热测。

## 历史执行与恢复设计（v0.0.17，恢复锁已在v0.0.19取消）

- 借鉴 mw-autotest 的串行调度与交接机制：用例结论和客户端恢复分别记录。单项失败、阻塞或中断，已恢复即可继续下一项；未完成正式热测不生成正式成功结果。
- 恢复未确认进入 `waiting_recovery`，保留后续计划，每5秒只读复查；也可点“重新核验恢复”。核验通过自动继续，不重跑失败项、不把它改成通过。用户暂停时恢复后停在暂停状态。
- worker 通过 IPC 上报阶段及不含原文的页面指纹。只有已证明专属清理全部完成，才允许按原页面、市场、搜索、草稿及无弹层状态复核放行；没有清理证据的强制中断继续等待，不能仅凭干净页面猜测技能、工作空间等已恢复。
- 超时只结束本脚本进程，等进程退出再交接。控制台保留最后阶段。手动停止取消剩余队列，但未恢复标记继续保留，新批次仍须核验。服务重启保留恢复等待，恢复后暂停，由用户继续。
- 011全量封面检查每张最多等3秒，滚动循环预算40秒；超时走既有清理逻辑，首屏计时与全量检查分开。恢复完成后可执行下一项。
- 轮询期间有拖选或选中文字时延迟重绘，取消选择后更新；后台任务继续运行。复制日志不会因1.5秒轮询失去选区。

框架来源：mw-autotest 的 `local-console/task-scheduler.mjs`、`task-recovery.mjs` 和服务端恢复循环。mw-auto 独立实现于 `lib/manager.mjs`、`lib/worker.mjs`、`lib/handoff.mjs`，不依赖父目录，可独立部署。44项入口及冷启动首页统一使用此worker生命周期；冷批次原进程或启动证据丢失仍停止，防止误标冷态数据。

## 启动和使用

v0.0.16 加固连续执行：新建任务、召唤专家和做同款使用本轮独立空间；清理后再次进入验证草稿，原空间草稿只在内存保存并复核。市场导航兼容直显页签与更多菜单，切换后校验目标内容；市场搜索从当前可见列表选样。详情中的“执行诊断”区分前置、自动化、断言及恢复异常，保留预热阶段记录，正式耗时仍只取第二次。恢复失败停止后续用例。

1. 启动 MobileWork 并完成登录，保持 CDP 开启。不要把 CDP 暴露到局域网。
2. 双击 `start.cmd`，或运行 `pwsh -NoProfile -File launch.ps1`。服务在后台运行，不自动重启客户端。
3. 打开上述本机地址，点击“重新检查”。勾选功能后点击“一键执行所选”，按重启弹框完成冷、热两轮；未勾选时可一键全部执行。单项“执行两轮”复用同一流程；仅需一轮时保留独立入口。
4. 运行时暂时不要操作 MobileWork。多个脚本串行执行。暂停/停止等待当前项结束并清理；继续不会重跑本批已完成项。
5. 点击功能名称查看原表要求、实际断言、未覆盖范围、状态恢复和性能口径。历史批次可查看、导出 JSON。

终端提交同一个串行队列：`node run.mjs MW-UI-014 MW-UI-015`。全量：`node run.mjs --all`。
诊断单个 worker：`node run-case.mjs MW-UI-014`，输出 JSON；不建议在控制台运行时并用。每个 worker 使用本机文件锁，防止同时操作客户端。

环境需要 Node.js 20+、现有捆绑 `playwright-core`；默认从当前用户 `.cache/codex-runtimes/codex-primary-runtime/dependencies/node` 加载。可用 `MW_PLAYWRIGHT_ROOT` 指向包含 package.json 的依赖目录。不需要 npm 下载，不需要 cmcc 部署。

## 数据与脚本

- 原始来源：下载目录的《MobileWork性能需求.xlsx》，`界面相应时间`第 4–47 行；未改动原 Excel。`接口响应时间`为空模板，`并发要求`未给出独立并发模型，因此没有伪造接口或并发验收。
- `data/cases.json`：44 项，保留源表行号、功能名、原始目标、冷热阈值。E 列描述有错位，仅保留原文，不用于推断测试通过。
- `cases/MW-UI-xxx.mjs`：一项一个脚本入口。共享交互实现位于 `lib/actions.mjs` 与 `lib/retry-actions.mjs`，通过真实 Playwright/CDP 控件操作与断言执行。
- `runs/<批次>.json`：时间、执行清单、结果、日志、断言、阻塞原因、性能样本、清理结果。历史结果保留，不覆盖失败记录。
- `data/server.*.log`：控制台服务日志。运行结果不存储令牌、Cookie、会话正文或完整 DOM，不自动截图真实历史任务。
- `探测结果.md`：交付时的实际复跑快照。控制台最近结果为后续实时记录。

## 结果解释

`pass` 只表示该脚本列出的断言通过；`partial` 表示只覆盖部分原表目标；`blocked` 表示前置条件不足、版本入口差异或缺少隔离夹具；`failed` 表示已进入测试但断言/执行/恢复异常。执行器异常为 `interrupted`，不能当成产品功能失败。

页面存在、入口可见和数据加载，不代表完整业务链路通过。市场搜索验证空结果与已知样本结果；筛选条件与分类选中样式只能部分证明结果正确。虚拟/分页任务列表的首批挂载，不等于所有任务加载。

状态变更采用 `finally` 清理：恢复模式、模型、技能/工具选择和原页面。工具开关只选择已连接工具，不启动新授权；技能只绑定已有项，不执行技能。初轮发现的开关动态名称、技能定位恢复问题已保留在历史中，修复后重新验证。清理异常必须人工核对原状态；队列自动停止后续项。

当前脚本不发送真实业务任务、不激活/补跑调度、不覆盖已有技能。v0.0.2 使用产品 UI 创建临时工作空间验证专家召唤及案例做同款；测试后清空草稿、退出新增绑定、先回到原空间再删除测试空间注册。安装技能按账户管理，只有基准技能原先未安装时才执行安装，并通过 UI 卸载恢复；若原先已安装则保留个人技能并标记前置受限。

## 性能边界

只有显式埋入的交互计时会记录 `measurements`：从渲染进程捕获输入事件，到脚本终态连续两次 requestAnimationFrame 成立。模式/模型还会重新打开菜单核对选中结果。

页面交互是 **Windows 热态参考**：v0.0.3 起预热 1 轮、记录后 2 轮，旧批次为单次记录；不是完整像素渲染完成，也不是统信/麒麟正式验收。应用冷启动另外记录于 `coldStart`，不与后续用例交互耗时混算。`totalExecutionMs` 包含准备、探测与清理，不能当响应时间。原表热态为“-”的项目不套用冷态阈值。`targetRelation: supporting` 表示补充场景，其计时不参与原表阈值比较；原场景入口缺失仍由 `originalScenario` 单独保留。无计时明确显示“未计时”，并不代表功能未执行。对有热态阈值的项目仅给出参考比较，不宣告目标平台达标。

## 冷热执行（v0.0.14）

- 每行提供“冷启动”和“热启动”。热态每个用例串行执行2次：第1次预热、不计入正式耗时，第2次为最终功能与耗时结果，不取均值。旧三轮均值标注为历史数据，不改写原记录。首次失败或恢复异常则保留异常并停止该项重复，不生成正式成功结果。
- 冷启动先弹出托盘退出说明，用户手动退出后点击“已退出，开始冷启动”；服务和 worker 都检查 MobileWork.exe 是否已全部退出。不会结束 MW 进程，也不会清空用户缓存或登录态。
- 从启动命令前计时，等待首页首屏、任务初始列表、工作空间及输入区就绪；必要的首页导航/展开、CDP 连接及观察开销包括在内。因此这是观察到就绪的耗时上界，不直接套用原表每个区域的性能阈值。
- 用例冷启动入口会先记录应用启动，然后执行该用例一次。启动后脚本准备可能预热目标模块，后续交互样本不能冒充该模块的严格冷加载；两类耗时分别存储于 `coldStart` 和 `measurements`。
- 冷、热结果及历史分别保留。v0.0.6 的“冷启动所选”每批只启动一次，后续所选用例复用同一进程自动执行；暂停后继续不重启。应用启动证据在批次 coldStart 与来源结果中，后续结果用 batchStartupRef 引用；原进程退出会停止后续项。失败、未完成正式执行或恢复异常均保留，不生成成功正式结果。
