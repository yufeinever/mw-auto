## 2. 判定以有效响应为中心

每个操作明确起点、结束条件、数据规模和观测来源，不用一个PASS/FAIL包办所有结论。

| 维度 | 建议状态 | 示例 |
| --- | --- | --- |
| 执行阶段 | preparing / ready / running / finished / stopped | “准备失败”与“操作超时”分别显示 |
| 样本有效性 | valid / timeout / not_measured / invalid | 超时无成功终点，不生成虚假的durationMs |
| 延迟比较 | within_target / exceeds_target / no_target / incomparable | 完成但慢是超标；不是内容失败 |
| 内容检查 | not_checked / matched / warning | 文案、分类内容核对默认补充记录 |
| 清理 | restored / warning / unknown | 计时850ms且清理异常，两者同时保留 |

保留旧functional、原始证据和历史解释；新记录增加版本化policy和分维度字段，不把旧失败批量改为通过。

需要保留的最小正确性条件：触发的是目标控件、终态属于当前Session/操作、确实从起始态发生变化、加载已经结束。任意DOM变化、任意200响应、出现错误页，都不能当成目标操作成功。动作前已满足终态时先在计时外恢复起点；无法恢复则记未测。

搜索允许明确空态，命中与未命中分开计时。命中场景若返回空态，可以记录“空态响应耗时+内容警告”，但不能混入“命中结果渲染”基准。空态不是所有场景的替代品：开关切换仍需存在可切换的开关。

测量超时与性能目标分离。例如目标200ms、观测截止10秒：实际800ms应得到有效的超标样本；10秒仍未结束则记录timeout、截止时间及观测状态，不填10000ms成功值。准备、操作、清理各有预算，慢机器不会因为耗时超过目标就立即被脚本中止。

## 3. 数据先准备，再开始测量

流程：机器能力检查 → 按所选用例生成准备计划 → 准备并验证资产 → 保存准备清单 → 重启确认（冷测时） → 串行执行 → 每条独立收尾 → 汇总。

准备器应幂等：同一个配方重复执行不会不断新建空间。每条用例的可变空间、Session、草稿和证据各自归属；只读素材包可共用版本，同一资产被多条复用时必须显式声明且不能修改。冷热两轮使用同一配方和起点，保存各自执行证据。

建议基础配方（数量是拟定基准，不是已有实现）：

- 固定版本的本地测试素材与专属工作空间；每条历史用例有独立已完成Session，包含固定轮数、字数和一种受控图片，搜索使用预置关键词。
- 空列表、标准列表两种场景独立命名；列表规模固定，并记录总数/已挂载数/可见数。真实用户数据模式只作现场参考，不纳入标准机器排名。
- 模型切换需要两个可用选项；优先配置稳定ID，无法获取ID时记录发现方式，不能按名称猜测同一资源。
- 技能选择用固定版本测试技能；下载安装用专用且未安装的样本，记录包版本、大小、缓存模式和来源。不得为准备卸载用户已有技能。
- 工具开关使用客户端实际支持接入的本地无副作用测试工具，只有完成真实注册并回读连接状态后才记ready。假开关或模拟网页只能验证脚本，不能充当产品性能。
- 案例/专家优先版本固定的测试素材或测试租户；若产品不支持导入，则从有权限的目录按所需能力发现对象，并标记为“动态目录参考”，不宣称固定基准。
- 自动化详情需要真实可打开的测试记录。若产品无合法导入方式，使用预先执行过的专用无副作用任务；生成该记录可能涉及执行与费用，必须独立声明，不能伪造成功数据库记录。

实现顺序：优先核实产品已有本地API或导入能力，再实现UI准备适配。当前没有验证可直接导入Session消息/自动化记录的接口，因此设计不假定其存在，不直接修改客户端数据库。不自动发送消息、调用外部服务或改个人账号配置来“补齐”环境；不能自动准备的能力列成明确的人工前置项，其他无依赖用例继续。

准备清单保存fixtureVersion、recipeHash、owner、稳定对象ID、客户端版本、必要数量与能力状态。对象创建前登记意图，创建后登记ID；延迟创建/准备崩溃后可以按本轮归属查找，缺归属不删除。清理失败保存残留清单，下一条从自己的起点执行，不恢复全局等待锁。

## 5. CDP和日志的采集边界

用户截图显示Electron主进程`[main][model-proxy]`日志。可见上游503及约40.8秒durationMs，随后还有stream_end、model_rewrite等记录。只能据截图确认这些事件存在，不能由局部截图确认完整调用链或最终业务成功。

| 来源 | 能可靠观察什么 | 不能据此推断什么 |
| --- | --- | --- |
| 页面CDP Network | 所附加目标能看到的请求、响应头/状态、接收数据、完成/失败、部分流事件 | 不能保证看到Electron主进程/独立引擎/代理的上游流量 |
| 页面DOM与渲染时钟 | 点击、局部可交互、首段答案出现、最终显示状态 | DOM变化不自动等于本次请求完成，必须绑定Session/消息 |
| 本地引擎结构化事件 | Session与消息进展、工具状态；以实际可用协议为准 | 不能默认事件已包括网关首token和重试细节 |
| 主进程结构化日志 | request_start、upstream_response、模型路由、fallback、stream_end及调用ID | stream_end completed只说明该流结束；日志耗时字段的语义须核实 |

现有实现的measure只采页面输入事件到DOM终态，尚未订阅Network或解析model-proxy日志。

建议新增只读观测器：CDP网络订阅 + 主进程日志增量读取 + 已验证的引擎事件适配。动作发生前订阅；主进程日志从本轮起始偏移读取，处理轮转、半行和重复事件。只保存允许的状态、计时、关联ID与模型身份等元数据，不复制请求头、认证信息、提示词或完整响应正文。

关联键分层：runId/caseId/round → sessionId/msgId → modelCallId或trace/span → 该来源的requestId。同一消息可有多次模型调用，不能按时间相近或最后一次200强行合并。无法证明关联时保留未关联事件，不计入该用例结论。CDP、页面performance和日志墙钟分别计时；跨时钟计算必须校准，不直接相减。

为响应类场景拆分指标：

1. 点击至界面反馈：页面时钟测按钮/加载态响应。
2. 请求至响应头：对应请求的Network时间，HTTP 503也保留为失败响应延迟。
3. 请求至首个有效输出（TTFT）：需要真正识别当前调用的文本/思考输出事件；首个SSE事件、心跳、角色字段或响应头都不能冒充首token。正文与思考可分别记录。
4. 请求至流结束：每个attempt独立记录status、duration、fallback和错误；流结束不等于业务成功。
5. 用户发送至最终完成：包含失败尝试、重试和等待，不能只展示最后一次成功的耗时。
6. 首段/最终答案在页面显示时间：与网络计时独立，DOM目标须绑定本Session和消息。

普通页面CDP不足时优先读已有日志。Electron主进程inspect需单独启用；不为正常性能测试打断点。netLog可作Chromium网络诊断，但不能假定覆盖Node网络库发出的全部请求。事件不可用时写“未采集”，不填0或推算token速度。

官方依据：[CDP Network](https://chromedevtools.github.io/devtools-protocol/tot/Network/)、[Electron主进程调试边界](https://www.electronjs.org/docs/latest/tutorial/debugging-main-process)、[Electron netLog](https://www.electronjs.org/docs/latest/api/net-log)。

## 6. 冷热与跨机器规则

- 准备资产可能预热页面、下载包、触发运行时加载；必须在冷启动重启前完成。重启后只做不改变目标起点的检查，不能重新创建数据再叫冷启动。
- 保留现有一次重启、首轮全部、第二轮全部的操作方式，但首轮明确叫“重启后首轮/共享进程”；真正独立冷加载需逐场景重启，属于另一实验。进程冷不代表磁盘/操作系统/服务端缓存冷。
- 第一轮安装、召唤、做同款产生的变化必须在第二轮前按配方复位。失败导致不可比则标记原因，不能默默换样本后比较冷热。
- 锁定Node及Playwright依赖并支持独立安装/分发，优先使用项目依赖，不要求其他机器拥有Codex运行时。
- CDP地址、客户端可执行路径、日志路径、超时配置单独存于本机配置；启动/进程发现按Windows/Linux/macOS适配。先做能力探测，未适配的平台禁用自动启动但可明确支持已启动连接的范围。
- 记录客户端/脚本/素材版本、OS/架构、CPU/内存概况、视口、缩放、网络来源、实际对象数量、缓存策略和可观测能力。全量清空个人缓存或改分辨率不能成为隐式操作。
- 只有配方、场景、终点、数据规模一致的样本才作跨机器比较。动态在线目录和生产个人数据只标现场参考。

## 7. 实施顺序与验收

第一阶段：准备失败分类、样本增量保存、结果维度分离；修复导航等待和当前态判断；同步manager、worker、CLI、前端、报告，保留所有历史。

第二阶段：建立准备计划、归属清单及版本化配方；逐项适配以上44个入口；先解决工具、历史Session、测试空间、固定名称依赖。需要产品接口而尚无能力的项明确保留前置，不通过造假规避。

第三阶段：接入只读CDP与主进程日志观测，增加独立的模型响应场景；不把原44项UI测试变成自动发送模型请求的测试。更新冷热流程与机器配置，再在目标设备验证。

本次仅设计，未新增或运行测试。实施验收预算明确为5项：①准备器场景（空数据、重复准备和准备超时分类）；②已完成样本在后续内容警告/清理异常时仍保留；③503→重试→最终结果关联且不把stream_end当成功；④机器A一个定向UI用例；⑤机器B用相同配方运行同一用例。不得通过另开子测试或拆轮次绕过总数上限；未执行跨机器实测前不宣称可移植验收完成。
